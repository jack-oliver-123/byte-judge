## 1. 本轮建设范围

后端采用 Maven 多模块工程：根聚合父工程下设置公共聚合层 `byte-judge-commons`、网关和业务聚合层 `byte-judge-models`；公共聚合层包含 `common-core` 公共协议库与 `common-web` 服务适配库，业务聚合层包含用户、题目、提交、竞赛、判题五个可独立启动的服务，统一使用单数后缀 `byte-judge-*-model` 命名。聚合层保留复数名称 `byte-judge-models`，网关保留 `byte-judge-gateway`。本轮建立模块、最小启动类、依赖管理、基础设施配置及启动验证入口，业务实现随后按服务归属加入。

“先不写业务代码”的落地边界是：允许各服务的 `XxxApplication.java` 启动入口；构建声明写入 `pom.xml`，运行配置写入 YAML，初始化与验收由脚本承载。Controller、Service、Entity、Mapper、业务 DTO、统一响应类、任务消费者和判题执行代码均不属于本轮交付。

文中的两类结构分别表示：

- **底座结构**：本轮工程搭建时计划实际创建的文件。
- **业务目录预览**：后续实现时的归属指引；按首个实际类创建目录，不批量生成空包或占位类。

本次仅编写结构预览。分支、源码、基础设施启动、ADR 与词汇表等后续交付按阶段推进；本文不表示已经构建或运行通过。

### 3.1 模块与运行职责

| Maven 模块 | 制品 / 运行方式 | 数据所有权 | 后续职责 |
| --- | --- | --- | --- |
| `byte-judge-commons` | 聚合父 POM，不启动、不注册 | 无 | 统一组织公共组件：common-core 与 common-web |
| `common-core` | 普通 jar，不启动、不注册 | 无 | 无框架依赖的统一响应、错误码与最小身份契约 |
| `common-web` | 普通 jar，不启动、不注册 | 无 | 显式装配的 MVC 错误出口、Security 错误出口、共享 Session Cookie 与请求日志 |
| `byte-judge-gateway` | Boot 可执行 jar | 无业务库 | MVC 网关、显式路由和入口保护 |
| `byte-judge-models` | 聚合父 POM，不启动、不注册 | 无 | 统一组织以下五个业务服务 |
| `byte-judge-user-model` | Boot 可执行 jar | `bj_user` | 用户、身份、资料、消息 |
| `byte-judge-problem-model` | Boot 可执行 jar | `bj_problem` | 草稿、不可变版本、测试数据及访问规则 |
| `byte-judge-submission-model` | Boot 可执行 jar | `bj_submission` | 提交、RUN、校验任务、执行协调、统计、调度 |
| `byte-judge-contest-model` | Boot 可执行 jar | `bj_contest` | 赛事、报名、正式榜及结算 |
| `byte-judge-judge-model` | Boot 可执行 jar | 无业务库账号 | 判题 worker，领取、执行及回报 |

根工程直接聚合 **3** 个子模块：`byte-judge-commons`、`byte-judge-gateway`、`byte-judge-models`。其中 `byte-judge-commons` 再聚合 **2** 个公共子模块，`byte-judge-models` 再聚合 **5** 个业务子模块；不含根工程共 **10** 个模块，含根工程共 **11** 个 POM，服务种类数仍为 **6**。提交服务和判题服务的双实例均复用同一制品，通过端口、实例 ID 和节点配置区分，不复制工程。第一轮底座验收先启动六类服务各一个实例；完整部署仍按 04 要求运行双提交实例、双判题实例。

公共组件采用“聚合层 `byte-judge-commons`、子模块 `common-*`”的命名约定。当前创建 `common-core` 与 `common-web`；`common-redis` 等组件待确有复用需求时再加入，当前不创建目录、POM 或依赖声明。`common-core` 保持无框架依赖的通用能力边界，`common-web` 只承载多个 Web 服务显式装配的 MVC / Security / Session / 日志适配，二者都不包含业务规则或业务实体。

命名采用“聚合层复数 `models`、业务服务单数 `model`”的约定：五个 `*-model` 子模块仍各自产出可执行服务，不作为共享 Entity / DTO 库；聚合层本身只包含 POM。五个服务的目录名、`artifactId`、`spring.application.name` 和 Nacos 注册名统一使用表中名称，网关服务发现目标同步引用新名称。04 §3.1 中五个 `*-service` 建议工程名由本文的新命名替代，职责、数据库及 API 路径沿用原设计。判题服务属于业务服务，聚合目录归属不改变其独立部署及沙箱隔离要求。

`PersistentScheduler` 在提交服务内保持独立的逻辑边界，本轮以 `scheduler` 包承载；04 中的“独立模块”在这里指服务内职责模块，不另增 Maven 子模块或独立调度服务。消息归用户服务，统计归提交服务，管理功能归各业务 owner。

### 3.2 Maven 依赖约定

- 父 POM 统一 Java 21、BOM、依赖版本和插件版本；Maven Enforcer 检查 Java 21，构建时显式选择已安装的 JDK 21，不修改全局 Java 默认版本。
- `byte-judge-commons/pom.xml` 继承根 POM，通过 `modules` 聚合 `common-core` 与 `common-web`；两个子模块以 `../pom.xml` 继承公共聚合父 POM。服务需要公共能力时显式依赖对应子模块，不把聚合 POM 当作代码依赖。
- `byte-judge-models/pom.xml` 继承根 POM，并通过 `modules` 聚合五个业务服务；五个业务服务以 `../pom.xml` 继承该聚合父 POM，继续获得根工程统一的依赖和插件管理。
- 六个服务分别声明自己使用的业务 starter；父 POM 用 `dependencyManagement` 管理版本，避免所有服务被动引入数据源、MQ 和 Session。`common-web` 自带 Web / Security / Session starter，只允许需要共享会话契约的网关和用户服务显式依赖，其他业务服务不得依赖它。
- Boot 打包插件仅在六个启动模块启用；根工程、`byte-judge-commons` 与 `byte-judge-models` 只聚合，`common-core` 与 `common-web` 保持普通 jar，均不执行可执行包重打包。
- 服务间通过 HTTP 契约或消息交互，不互相依赖可执行服务模块，不共享 Entity、Mapper、数据库账号。
- `common-core` 只承载无框架依赖的共享契约（统一响应、错误码、最小会话身份）；后续新增类型须保持该边界，避免演变成包含业务实现的公共模块。

### 4.2 功能优先的服务内分层

以下示例以 `byte-judge-models/byte-judge-submission-model` 的 Java 包为根。业务实现采用按职责划分、内部再分层的结构；本轮只创建上一节所列启动类和配置文件。

```text
com/jack/bytejudge/submission/
├── SubmissionApplication.java
├── config/                             # 服务装配与技术配置
├── admission/                          # AdmissionCoordinator：许可与持久受理
│   ├── interfaces/                     # 外部 / 内部协议入口及 DTO
│   │   ├── http/                       # 浏览器接口
│   │   │   ├── controller/
│   │   │   ├── dto/                    # HTTP 请求对象
│   │   │   └── vo/                     # HTTP 响应对象
│   │   └── internal/                   # 服务间入口及其独立协议对象
│   ├── application/                    # 用例编排、事务边界
│   │   ├── command/                    # 写用例输入
│   │   ├── query/                      # 读用例输入
│   │   ├── result/                     # 应用结果
│   │   └── port/                       # 用例所需的外部能力接口
│   ├── domain/                         # 规则、领域模型及所需 Port
│   │   ├── model/                      # 领域实体、值对象与状态
│   │   └── repository/                 # 领域存储接口
│   └── infrastructure/                 # 数据库、HTTP 等 Adapter
│       ├── persistence/
│       │   ├── entity/                 # 数据库映射对象
│       │   ├── mapper/                 # MyBatis Mapper 接口
│       │   └── repository/             # 领域存储接口的实现
│       ├── client/                     # 外部 HTTP 客户端及协议转换
│       └── messaging/                  # MQ 发布 / 消费适配
├── execution/                          # ExecutionCoordinator：轮次、尝试、执行权
├── statistics/                         # 个人统计与题目统计事件
├── scheduler/                          # PersistentScheduler：计划、触发及副作用许可
└── infrastructure/                     # 本服务共享的 Outbox / Inbox / 审计设施
```

`execution`、`statistics`、`scheduler` 在出现实际实现时按同样的分层规则展开；包的层级服务于职责，不要求每个小功能都生成四层。源码依赖方向为 `interfaces → application → domain`，`infrastructure` 实现领域或应用所需的 Port，通过配置装配；领域规则不依赖 Controller、Mapper 或沙箱客户端。

功能包对外暴露所需的应用入口，其他功能包通过该入口协作，不直接调用其 Controller、Mapper 或存储实现。应用编排不能只作为无行为的转发层；纯规则无需为了目录齐全而强行增加接口或实现类。

### 4.3 对象与外部集成归属

| 类型 / 能力 | 归属位置（相对功能包） | 使用约束 |
| --- | --- | --- |
| 浏览器请求 DTO、响应 VO | `interfaces.http.dto`、`interfaces.http.vo` | 协议校验与字段白名单在入口转换；不直接充当持久化或领域对象 |
| 服务间 HTTP 协议对象 | `interfaces.internal` 下按需分包 | 独立于浏览器协议，响应仅包含调用方获授权的数据 |
| 应用命令、查询、结果 | `application.command`、`application.query`、`application.result` | 面向用例，不依赖 Servlet 请求或 HTTP 注解 |
| 领域实体、值对象、状态 | `domain.model` | 业务规则归本服务、本功能；不直接作为 HTTP 响应 |
| 数据库映射对象、Mapper | `infrastructure.persistence.entity`、`infrastructure.persistence.mapper` | MyBatis-Plus 注解限于持久化对象，数据库对象不跨服务共享 |
| 存储实现 | `infrastructure.persistence.repository` | 实现领域存储接口，负责领域对象与持久化对象转换 |
| 外部 HTTP 调用 | `infrastructure.client` | 实现应用所需 Port，隔离远程 DTO、超时与协议细节 |
| MQ 发布与消费 | `infrastructure.messaging` | 消费入口转换消息后交给应用用例，业务去重和事务由所属用例编排 |
| 沙箱调用 | 判题服务的 `execution.infrastructure.sandbox` | 实现 SandboxExecutor 所需接口，隔离候选 go-judge 协议与底层状态 |

领域存储接口归 `domain.repository`，仅供用例编排使用的外部能力接口归 `application.port`；接口放在实际使用它的层，避免在多个层重复声明同一接口。对象转换放在对应协议或存储适配处，只有存在实际复用时才增加专门的转换类；不把转换逻辑、业务 DTO 或全部业务错误码集中塞入公共库。

### 4.4 各服务功能归属

其他服务按下面的边界展开，各服务自己的 Outbox、Inbox 和审计实现留在本服务内：

| 服务 | 后续功能包建议 | 架构落点 |
| --- | --- | --- |
| gateway | `config`、`security`、`observability` | 显式路由、内部路径拒绝、入口身份和追踪 |
| user | `account`、`auth`、`profile`、`message` | 账户状态与角色分离、Session 撤销、消息去重 |
| problem | `problem`、`version`、`validation`、`artifact`、`access` | 草稿与快照分离、校验证明、受保护文件、ProblemAccess |
| submission | `admission`、`execution`、`statistics`、`scheduler` | 受理闸门、执行权、统计、持久调度 |
| contest | `contest`、`registration`、`standings`、`notification` | 发布与报名、ContestStandings、结算屏障、通知事件 |
| judge | `task`、`execution`、`comparison`、`artifact` | 任务领取续租、执行编排、token 比较、数据校验；沙箱适配位于 `execution.infrastructure.sandbox` |

后续需要数据库迁移时，各数据 owner 使用自身 `src/main/resources/db/migration/`；需要 MyBatis XML 时放在自身 `src/main/resources/mapper/`。规则测试、集成测试分别随对应功能进入 `src/test/java/`，必要的测试材料放在 `src/test/resources/`。底座不生成空业务迁移、示例业务表或 Mapper。

MyBatis XML 在 `resources/mapper/` 下继续按功能分目录，例如 `mapper/admission/`，namespace 与对应 Mapper 接口全限定名一致。测试包跟随被测试功能的 Java 包结构，方便定位规则、用例与适配的验证入口。

### 4.5 common-core 的公共能力边界

`common-core` 使用 `com.jack.bytejudge.common.core` 根包，当前包含 `response`（统一 `code/data/message/requestId/serverTime` 响应与冻结的错误码）和 `security`（跨进程共享的最小会话身份 `SessionIdentity`）。后续可按实际需要加入 `error`、`pagination`、`util` 等基础包；所有类型保持无框架依赖。

业务实体、数据库映射对象、Mapper、业务状态与规则、各服务请求 DTO 和响应 VO 均留在所属服务。稳定跨服务契约确需共享时，另行明确其所有者与版本兼容规则，不直接搬入公共库形成共享业务模型。`SessionIdentity` 是当前唯一的共享身份契约：它只含用户编号、规范化账户和角色，由 `common-core` 统一版本管理，网关与用户服务必须使用同一制品版本。

`common-core` 不承担 Redis、MySQL、RabbitMQ、Spring Security 等专用能力的客户端配置、自动配置或业务实现。需要 Spring 适配的公共代码放在 `common-web`，由服务通过 `@Import` 显式装配，不通过扩大组件扫描范围隐式引入；`common-web` 同样不得包含业务规则、业务实体或服务私有 DTO。

## 5. 本地运行材料与配置边界

本地运行形态为 **Docker Compose 承载四件基础设施，IDE 或 Maven 启动六个 Java 服务**。`compose.yaml` 本轮不加入 Nginx、前端、go-judge，也不为各 Java 服务生成 Dockerfile。判题服务可启动和注册，但在沙箱能力未验证时保持不接业务任务。

| 位置 | 保存内容 | 约束 |
| --- | --- | --- |
| 父 / 子模块 POM | 构建、依赖、打包声明 | 版本统一管理，服务按需引用 |
| `application.yml` | 服务名、公共默认项、变量引用 | 不存真实凭据；不复制旧 `bootstrap.yml` |
| `application-local.yml` | 本机开发覆盖项 | 基础设施地址、端口及配置中心接入方式待下一轮确定 |
| `.env.example` | 本地环境变量清单 | 可提交，占位值不可冒充有效凭据 |
| `.env.local` | 本机生成的实际变量 | 忽略，不提交；提供给 Compose 和启动会话 |
| `infra/mysql/init/` | 建库、独立账号和授权模板 | 只负责基础设施初始化，不承载业务表演进 |
| `infra/nacos/` | 初始化和配置导入说明 | 若本轮接入配置中心，再补配置模板及导入脚本 |
| Compose 命名卷 | MySQL、Nacos、Redis、RabbitMQ 持久材料 | 生命周期与源码分离，常规停止保留数据 |

本地初始化按变量生成四个服务账号，各账号仅获所属库权限；gateway、judge 不分配业务库账号。数据库 init 材料在空数据卷初始化时执行，后续变更通过受控步骤或 Flyway 迁移，不能假设重启会重跑初始化。

本地基础设施端口仅绑定回环地址。第一轮接受了本地 Nacos 关闭鉴权的隔离调试方案；该配置只用于本机开发，部署阶段使用独立凭据与鉴权。具体端口映射、Nacos 配置中心是否在本轮启用，以及管理端点的访问方式，保留为后续配置决策。

## 6. 底座启动验收

本轮采用第一轮推荐的 B 口径：**构建 + 基础设施 + 六服务启动注册 + 健康检查 + 网关发现与转发**。

| 顺序 | 验证项 | 通过证据 |
| --- | --- | --- |
| 1 | 后端根目录执行 `mvnw.cmd clean package` | Java 21 构建通过；六个服务产出可执行 jar，common-core 产出普通 jar，三个聚合工程保持 POM 制品 |
| 2 | 启动本地四件套 | Compose 健康状态及各基础设施可连接；四库、独立账号与权限正确 |
| 3 | 启动六个服务 | 各自启动成功、无必需配置错误，Nacos 中出现六个正确服务名及健康实例 |
| 4 | 检查各服务 Actuator | 六个服务的 `/actuator/health` 为 UP，所需依赖另由连接检查证明 |
| 5 | 验证四条下游服务路由 | 用户、题目、提交、竞赛各选一条 04 §2.3 路径，经服务发现转发到正确下游；业务接口未实现时预期下游 404 |
| 6 | 证明响应来自下游 | 结合下游访问记录，或短暂停止目标实例后观察无可用实例错误、恢复后重现下游 404；单独收到 404 不算转发证据 |
| 7 | 记录启动结果 | README 记录实际命令、变量、地址、检查结果及限制；脚本发现失败返回非零退出码 |

路由规则显式按 04 §2.3 配置，不开放按服务名自动映射全部端点的 discovery 路由。judge 不面向浏览器转发，`/internal/v1/**` 及下游 Actuator 不经公共网关暴露。

Actuator 的 UP 在底座阶段仅证明已配置的健康项正常；还需分别检查 Nacos、数据库、Redis 和 RabbitMQ 连接。本轮不以 UP 宣称 Session 撤销、可靠消息、双节点任务处理或沙箱隔离通过。完整 readiness、liveness 和故障语义继续依据 04 §14.3 实现。
